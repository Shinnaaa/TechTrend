## 🧠 AI/ML 前沿论文

**[OpenForgeRL: Train Harness-native Agents in Any Environment](https://huggingface.co/papers/2607.21557)**
🔬 突破：推翻“复杂的 agent harness（如 Claude Code、Codex）无法端到端训练”的假设。OpenForgeRL 通过一个轻量级代理（proxy）截获 harness 的模型调用，将多轮推理、工具使用和状态管理暴露为 RL 环境，首次实现**在原始 harness 上直接应用 PPO/SFT**。在 SWE-bench 上，训练后的 agent 相比基线提升 23% 功能成功率。
⚙️ 工程影响：当前所有 coding agent 开发者（如 Cursor、Continue 团队）可用此框架将自己的 harness 接入 RL 训练，不再需要重写推理循环；预计 1 个月内会出现基于 OpenForgeRL 的 Codex 训练插件。

**[SANA-Video 2.0: Hybrid Linear Attention with Attention Residuals for Efficient Video Generation](https://huggingface.co/papers/2607.21553)**
🔬 突破：提出混合线性-软注意力（3:1 比例），在保持 O(N) 复杂度同时通过“注意力残差”恢复全秩交互，消除纯线性注意力的容量损失。在 14B 参数规模下，单 GPU（A100 40GB）生成 720p 视频（128 帧）仅需 12 秒，质量匹配 full-softmax DiT（如 Open-Sora Plan），但速度提升 4.2倍。
⚙️ 工程影响：视频生成模型的推理成本将骤降——之前需要 8×A100 的任务现在单卡可完成；建议关注其权重何时开源，可用于替换当前的 slow DiT 部署方案。

**[Sample-Efficient Learning from Agent Experience](https://huggingface.co/papers/2607.21051)**
🔬 突破：提出“上下文蒸馏”机制——将 agent 与环境的交互历史作为上下文让模型学习，然后通过蒸馏固定到权重中，使得模型在下一次任务中不需要再次交互就能获得类似效果。在 HomePage 任务列表上，样本效率相比纯 ICL 提升 3.2 倍，且收益不因上下文清除而丢失。
⚙️ 工程影响：这对所有需要“累积经验”的 agent 系统（如任务调度、客服机器人）有直接价值：可将历史对话蒸馏进模型，避免每次从头推理；建议在本周内阅读其蒸馏 loss 设计，评估是否适用于自己团队的 agent 记忆架构。

## 💬 Hacker News 技术热点

**[Android may soon restrict on-device ADB](https://kitsumed.github.io/blog/posts/android-may-soon-restrict-on-device-adb/)** 👍941 💬459
🗣 社区争论核心：Google 计划在 Android 16 中**限制通过无线调试（Wireless Debugging）或 ADB over Wi-Fi 的 on-device 调试**，仅允许通过 USB 连接电脑。这意味着所有依赖 on-device ADB 的自动化工具（如 UI 录制、无 root 的自动化测试、游戏外挂）将失效。评论区高赞指出，该限制主要是为了阻止恶意应用滥用 ADB 权限安装静默应用，但开发者将被迫恢复有线调试。工程结论：如果你的团队有 Android 设备农场（如 Firebase Test Lab），需在 Android 16 落地前测试无线调试兼容性，否则 CI 流水线可能断裂。

**[The new rules of context engineering for Claude 5 generation models](https://claude.com/blog/the-new-rules-of-context-engineering-for-claude-5-generation-models)** 👍348 💬236
🗣 Anthropic 发布 Claude 5 的上下文工程新规则，核心变化：Claude 5 对**上下文顺序敏感性降低**，但对**上下文“密度”更敏感**。具体来说，模型不再因关键信息在后半段而忽略，但低信息密度区域（重复、冗余）会稀释注意力。社区测试反馈：在 200K 上下文中，将 50 个指令/规则放在前十行，相比均匀分布，生成质量提升 12%。工程结论：所有 prompt 策略需从“位置优先”转向“密度优先”——每个 token 必须有独立价值，否则应裁掉。

**[Running a 28.9M parameter LLM on an $8 microcontroller](https://github.com/slvDev/esp32-ai)** 👍198 💬47
🗣 在一个 ESP32-S3（240MHz、8MB SRAM）上成功运行了一个 28.9M 参数的小型 transformer，使用 4-bit 量化 + 一步推理，token 生成速度约 0.3 tokens/s。核心工程技巧：将权重分片存储在 PSRAM，并使用 Xtensa 汇编优化矩阵乘法。社区争议点：是否真的有实用价值——0.3 t/s 只能做简单分类或关键词提取，但功耗仅 0.5W。工程结论：这为“无网络边缘设备场景”（如工业传感器、门锁）提供了低成本语音/文本分类方案，但非对话用途。
